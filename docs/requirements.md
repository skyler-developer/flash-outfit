# 闪搭 · MVP 需求文档

> 版本：v1.2（需求收敛完成）
> 状态：作为后续开发的唯一需求源，每轮需求变更由讨论确认后更新此文档
> 说明：本产品为"寻找搭子"类小程序，通过发布/浏览/申请"找搭子请求"实现快速组伴

---

## 1. 产品定位

**闪搭**——快速找到一起做某件事的人。核心价值主张是"**闪**"：轻量、即时、低承诺。

- 产品形态：请求流 + 申请制。发布者发布"找搭子请求"，浏览者申请加入，发布者审批后成组
- 区别于重流程的传统组局产品：表单极简（一张表单 + 快捷时间选项）、成组即交换联系方式、站外自行联系
- 合规基调：定位为"**兴趣活动搭伴工具**"，避免"交友"等敏感表述，社交类目资质需提前规划

## 2. MVP 范围

### 2.1 In Scope（第一版目标）

- 微信授权登录 + 用户资料（头像/昵称/性别/年龄/微信号/兴趣标签）
- 发布真实请求（复用现有发布表单）+ 图片上传
- 首页请求流：上下滑动浏览，默认 LBS 距离排序 + 手动筛选
- 请求详情页
- 申请制：申请加入（必附留言）→ 发布者审批 → 成组（发布者可设人数上限，默认 1 人）
- 成组后互见微信号，站外联系
- 消息页 = 通知中心（申请提醒、审批结果等系统通知）
- TabBar 调整为 4 tab：首页 / 消息（通知中心）/ 发布 / 我的
- 自建后端：**NestJS**，与前端同仓库（`server/` 目录）；API 契约由本方先行起草（`docs/api-contract.md`），后端按契约在本项目内实现

### 2.2 Out of Scope（MVP 明确不做）

- 站内 IM / 私聊
- 独立匹配页、系统撮合、滑卡配对（匹配页已从 MVP 移除）
- 评价体系、搭子历史
- 支付相关

### 2.3 后端技术选型（已定）

| 项 | 选型 | 理由 |
| --- | --- | --- |
| 框架 | NestJS（`server/` 目录，与前端同仓库） | 已定 |
| 数据库 | **MySQL 8**（云 RDS） | 阿里云/腾讯云 RDS 均为主流且便宜；TypeORM 支持成熟；距离计算用 Haversine 公式 SQL 实现，MVP 无需 PostGIS |
| ORM | **TypeORM**（@nestjs/typeorm） | NestJS 官方生态集成最成熟，国内文档多 |
| 图片存储 | **StorageService 抽象层**：开发阶段本地静态目录（`server/uploads/`），上线切阿里云 OSS / 腾讯云 COS（仅切换适配器，不动业务代码） | 先本地验证后平滑上云 |
| 鉴权 | JWT（登录态短 token，过期重新静默 wx.login 换发，MVP 不做 refresh token） | 小程序端无第三方态，静默续期成本低 |
| 部署 | 云服务器（ECS/CVM）+ HTTPS 备案域名 + pm2 或 Docker | 小程序 request 合法域名强制 HTTPS + ICP 备案；开发工具阶段可勾选"不校验合法域名"联调 |

## 3. 核心用户流程

```
登录授权 → 完善资料（性别/年龄/兴趣标签/微信号）
   ↓
发布者：发布请求（现有表单）→ 请求进入首页流 → 收到申请通知 → 查看申请人资料+留言 → 审批 → 成组 → 互见微信号
   ↓
浏览者：首页流（默认距离排序，可筛选）→ 查看请求详情 → 申请加入 + 填写留言 → 等待 → 收到审批结果通知 → 成组则互见微信号
```

## 4. 页面需求

### 4.1 TabBar（4 tab，需改造现有 5 tab）

| Tab | 页面 | 说明 |
| --- | --- | --- |
| 首页 | pages/home | 请求流（唯一浏览入口） |
| 消息 | pages/message | 改造为**通知中心**，非 IM |
| 发布 | pages/publish | 中央凸起按钮（保留现有样式） |
| 我的 | pages/mine | 个人中心 |

匹配页（pages/match）从 MVP 移除，tabBar 与路由配置同步删除。

### 4.2 首页（pages/home）

- 请求卡片流：上下滑动浏览，卡片需升级为展示「活动类型 / 标题摘要 / 时间 / 目的地 / **距你 x km** / 发起人头像昵称 / 伙伴偏好标签」
- 排序：默认 LBS 距离排序；进入小程序时请求一次定位授权并缓存坐标
- 筛选器（手动选择）：
  1. **活动类型**：旅行 / 摄影 / 运动
  2. **时间范围**：本周末 / 近 7 天 / 近 30 天 等
  3. **距离范围**：如 5km / 10km / 50km / 全城 / 不限
  4. **只看可申请**：过滤掉我不符合其伙伴偏好的请求（性别或年龄不符合的不再展示/置灰）
- **过期标记**：活动时间已过但发布者未手动结束的请求，MVP 不做状态自动流转，在首页浏览时实时标记「已过期」（置灰/角标），不可申请
- 下拉刷新、上拉加载更多
- 点击卡片 → 请求详情页

### 4.3 发布页（pages/publish，已有 70%）

保留现有表单结构，**新增字段**：

- **搭子人数上限**：发布者自行设置，默认 **1 人**（人数上限内的申请逐个审批）
- **成组后是否自动结束招募**：发布者自行设置开关，默认**不结束**（不结束时成组后仍继续招募，直到手动结束或满员）

补齐现有占位：

- 提交对接真实接口（替换现有 setTimeout 模拟）
- 图片真实上传（替换现有本地临时路径方案）
- 逆地理编码真实化（替换现有写死"上海"的占位）
- 微信号**强制引导**：提交前校验用户已填写微信号（成组刚需），未填则阻断提交并引导去资料页，填写后返回不丢失已填表单

### 4.4 请求详情页（新页面，MVP 必需）

- 完整信息：大图照片（可滑动）、活动类型、时间、目的地+距离、发起人资料卡（头像/昵称/性别/年龄/兴趣标签）、伙伴偏好、完整描述
- 底部操作：「申请加入」→ 弹出申请弹窗
- 状态展示：招募中 / 已成组 / 已结束（不可申请）

### 4.5 申请流程

- **申请弹窗**（新组件）：必填一句话留言（自我介绍/参与意愿，建议限长 100 字），提交
- **申请状态**：待审批 → 已同意 / 已拒绝
- **满员校验**：已通过人数达到人数上限即满员，满员后新申请不可提交（提示"已满员"）、待审批申请不可再通过；**满员后其余 pending 申请保持不变**，由发布者自行处理（只能拒绝，MVP 无退出/释放名额机制）
- 防重复申请：同一请求不可重复申请；待审批期间不可再次提交

### 4.6 请求管理（发布者视角，新页面）

- 入口：我的页 →「我发布的请求」→ 请求管理
- **修改**：发布者可随时编辑自己发布的请求（类型/时间/地点/偏好/描述/照片/人数上限/自动结束开关）；修改保存后不通知已申请者（MVP 简化）
- **删除**：发布者可随时删除自己的请求；删除时向该请求所有申请人发送通知（requestClosed），已成组（approved）的申请人同样收到通知，微信号交换关系至此终止
- **申请管理**：每个申请展示：申请人资料卡（头像/昵称/性别/年龄/兴趣标签）+ 申请留言
- 操作：同意 / 拒绝；同意后该申请进入"已成组"，双方互见微信号（申请人在「我的申请」中可见发布者微信号；发布者在申请管理中可见申请人微信号）；多人请求逐个审批，直到满员
- 同意/拒绝后向申请人推送通知

### 4.7 消息页 = 通知中心（pages/message 改造）

MVP 通知类型：

1. 收到新申请（发布者）：「xx 申请加入你的『xxx』」→ 点击进入审批
2. 审批结果（申请者）：「你的申请已被通过/拒绝」→ 成组则展示对方微信号入口
3. 请求状态变化：如我申请的请求已结束/被取消

### 4.8 我的页（pages/mine，新开发）

- 用户资料卡：头像 / 昵称 / 性别 / 年龄 / 兴趣标签 / 微信号（可编辑）
- 入口列表：我发布的请求（含申请管理）、我的申请（含状态）、编辑资料、社区公约

### 4.9 登录与资料（新流程）

- `wx.login` + 自建后端 code2Session，静默登录
- 资料引导页：性别、**出生年份**必填（年龄由出生年份自动计算，不随时间过期；伙伴偏好筛选依赖）；兴趣标签多选（旅行/摄影/运动，用于卡片展示）；微信号引导填写（发布时强制校验，成组刚需）
- 头像昵称：使用微信"头像昵称填写能力"（open-type/avatar 昵称 input），用户确认后入库

## 5. 数据模型（草案，供后端契约参考）

```
User:        id, openid, nickname, avatar, gender, birthYear, age(派生), wechatId, interests[], createdAt
Request:     id, publisherId, type(travel|photography|sports), activityTime,
             destination, location(lat,lng,city), genderPreference(all|female|male),
             ageRange[min,max], maxMembers(默认1), autoCloseOnGrouped(默认false),
             approvedCount(派生), description, photos[],
             status(recruiting|grouped|finished|cancelled), expired(派生), createdAt
Application: id, requestId, applicantId, message, status(pending|approved|rejected), createdAt, handledAt
Notification:id, userId, type(newApply|applyApproved|applyRejected|requestClosed), relatedId, isRead, createdAt
```

请求状态机：`recruiting（招募中）→ grouped（已成组）→ finished（手动结束）`，任意状态可 `cancelled`（含发布者删除）。
申请状态机：`pending → approved | rejected`（发布者删除请求时，MVP 不改写存量申请状态，仅发通知）。

派生字段说明：

- `age`：由 birthYear 与当前年份计算，不落库
- `approvedCount`：该请求下 approved 申请数，用于满员校验
- `expired`：activityTime 已过且 status 仍为 recruiting/grouped 时，**浏览时实时计算**的展示标记（首页标记"已过期"），MVP 不落库、不自动改状态

## 6. 关键规则

- **成组人数**：发布者设置人数上限（默认 1），逐个审批多人；`approvedCount ≥ maxMembers` 即满员，满员后不可再通过/新申请，剩余 pending 保持不变由发布者自行处理
- **自动结束招募**：发布者发布时设置（默认不结束）；开启时首个申请 approved 后请求自动进入 `grouped`；关闭时成组后继续招募，直到手动结束或满员
- **请求修改/删除**：发布者可随时修改/删除自己的请求；修改不通知已申请者，删除通知全部申请人（含已成组）；删除后申请人的待审批申请同步失效提示
- **过期处理**：活动时间过后 MVP 仅在首页浏览时实时标记「已过期」，不做状态自动流转
- **伙伴偏好执行**：请求的性别/年龄偏好在申请时校验，不符合者不可申请（提示原因）；首页"只看可申请"过滤器联动
- **联系方式披露**：仅成组（申请 approved）后双方互见微信号；任何其他页面不展示微信号
- **LBS 策略**：进入小程序时一次性请求定位（非持续），缓存坐标用于距离计算与排序；拒绝授权则降级为**「选择城市」模式**：用户手动选城市，按该城市展示并回退时间倒序排序
- **微信号校验时机**：发布时强制校验并引导填写；申请时不强制（未填微信号的用户可申请，成组后引导补填后方可见对方微信号）
- **内容安全**：发布描述与图片需接入内容安全审核（msgSecCheck/imgSecCheck 或后端等价能力）；照片必传（1~6 张）以保障请求可信度
